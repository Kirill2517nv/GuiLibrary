# Архитектурное ревью учебного API

## Что в текущем подходе удачно

- Код физической модели отделён от GLFW, OpenGL, ImGui и главного цикла.
- Параметры адресуются понятными строковыми именами; ученику не нужны указатели
  и владение объектами GUI.
- `set_calculation_function` задаёт простой жизненный цикл «один шаг — один
  кадр», подходящий для первых моделей.
- Именованные графики позволяют постепенно перейти от одного окна к нескольким.
- ImGui/ImPlot/GLFW зафиксированы сабмодулями, поэтому сборка воспроизводима.

## Основные проблемы

1. `DataArray` — деталь хранения, но находится в публичном API и в коде модели.
   Его публичные поля (`x`, `y`, `head`) позволяют нарушить инварианты. Методы
   `getX/getY` копируют до 20 000 элементов дважды на каждом кадре.
2. `Scale` используется как временная упаковка четырёх чисел, хотя масштаб уже
   принадлежит `PlotData`. Для учебного примера это лишнее понятие.
3. Глобальные `t`, `buffer`, `scale` и callback-функции затрудняют повторный
   запуск модели и тестирование без GUI.
4. Строковые ключи параметров удобны в начале, но опечатка обнаруживается лишь
   во время выполнения. Неизвестный параметр сейчас не даёт ученику достаточно
   заметной диагностики.
5. `clear_plot` означает «удалить объекты кадра», а не «забыть историю»; имя без
   пояснения двусмысленно.
6. Библиотека хранит всё состояние в статических глобальных контейнерах. Это
   допустимо для одного учебного приложения, но мешает модульным тестам,
   повторной инициализации и нескольким экземплярам приложения.
7. Отрисовочные структуры копируют векторы. Для больших серий это создаёт
   лишние выделения памяти и копирования на каждом кадре.

## Реализованный промежуточный фасад

Для `Task_1` добавлены три операции:

```cpp
create_plot("Sin", 0.f, 200.f, -2.f, 2.f, 750, 475);
add_plot_history_point("Sin", t, y, "sin", BLUE, 1.f, 20000);
clear_plot_history("Sin");
```

Каждая именованная история теперь входит в `PlotData` и использует внутренний
кольцевой буфер. ImPlot получает данные напрямую без создания двух временных
векторов. `clear_plot` продолжает очищать объекты текущего кадра; история живёт
до явного `clear_plot_history`. Старый API сохранён, поэтому остальные задания
можно переносить по одному.

## Целевой API

После проверки промежуточного фасада на заданиях 1–3 стоит перейти к объекту
приложения и дескрипторам вместо глобального реестра и строк в каждом вызове:

```cpp
GuiApp app("Колебания");
auto pause = app.checkbox("Pause", false);
auto amplitude = app.number("Amplitude", 1.f);
auto plot = app.plot("Sin", AxisRange{0, 200}, AxisRange{-2, 2});
auto history = plot.history("sin(t)", 20000, BLUE);

app.on_restart([&] {
    t = 0.f;
    history.clear();
});

app.on_step([&] {
    if (pause.value()) return;
    t += dt;
    history.add(t, amplitude.value() * std::sin(t));
    plot.marker("current", t, history.last_y(), RED);
});

return app.run();
```

У такого API ясное владение: `GuiApp` владеет окнами и параметрами, `Plot`
владеет сериями, `History` владеет данными. Дескрипторы валидируются при создании,
поэтому опечатки не повторяются каждый кадр. Для школьного курса можно оставить
свободные функции как тонкий фасад над единственным `GuiApp`, а объектный слой
использовать внутри библиотеки и в продвинутых заданиях.

## Рекомендуемый порядок миграции

1. Проверить визуально уже перенесённые `Task_1`, `Task_2` и `Task_3`, включая
   начальные точки и поведение кнопки Restart.
2. Спрятать `DataArray`, `PlotData` и отрисовочные структуры в `detail`/`.cpp`;
   оставить их временно в deprecated-заголовке для старых работ.
3. Ввести `GuiApp` как владельца текущих `g_parameters`, `g_plots` и lifecycle.
4. Добавить `Simulation` с методами `reset()` и `step(dt)`, не зависящими от GUI;
   отдельно тестировать численный метод и отдельно адаптер визуализации.
5. Добавить диагностические сообщения для дубликатов графиков, неверных имён и
   несовпадающих размеров `x/y`, затем тесты на кольцевой буфер и reset.
